# Consumer tooling

> Optional development and quality tooling for applications generated by the published Atlas CLI.

The default `atlas init` baseline is practical: Doctor, lint, typecheck, unit tests, production
build, and local Lighthouse/bundle commands. Heavier tooling is **opt-in** through `atlas enable`.
Atlas publishing, release rehearsal, internal governance, and BlitzCraft runners stay
maintainer-only.

**Generated projects pin the Atlas CLI.** After `pnpm install`, use `pnpm atlas`. Historical npm
`1.1.0` did not contain `atlas enable`. Projects created by a CLI that includes `enable` run it
locally; `atlas upgrade` does not install optional tooling.

```bash
pnpm atlas enable list --json
pnpm atlas enable storybook --dry-run
pnpm atlas doctor
pnpm atlas upgrade --dry-run
```

`pnpm dlx @blitzcraftlabs/atlas init <name>` remains the bootstrap before a consumer repository
exists.

## Default baseline

| Capability                      | How                                                                                          |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| Atlas Doctor                    | `pnpm atlas doctor`                                                                          |
| Lint / typecheck / test / build | `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`                                     |
| Consumer GitHub CI              | `.github/workflows/ci.yml` (GitHub-hosted Ubuntu)                                            |
| Local performance               | `pnpm start`, `pnpm perf:lhci`, `pnpm perf:analyze` (no CI workflows until `enable perf-ci`) |
| Container build files           | Root `Dockerfile` and `.dockerignore` (repository-level Atlas templates)                     |
| OpenAPI client                  | `pnpm api:gen`                                                                               |

## Opt-in capabilities

`atlas enable list --json` reports `status`, not a boolean “enabled that works”:

| Status        | Meaning                                                                       |
| ------------- | ----------------------------------------------------------------------------- |
| `absent`      | None of the packaged/generated files or package keys are present              |
| `partial`     | Some files/keys are present, others are missing                               |
| `installed`   | Files and package keys match the packaged/generated copies                    |
| `conflicted`  | At least one present file or package key differs from Atlas                   |
| `replaceable` | Documentation matches a known unmodified shipped checksum and can be replaced |

`installed` / `filesMatch` means layout matches. It does **not** mean `validationCommand` passed or
that Storybook, Docker, coverage, or hooks are operational. Each capability lists
`validationCommand`.

| Id          | Adds                                                   | Heavier?               | Validate                                                                                |
| ----------- | ------------------------------------------------------ | ---------------------- | --------------------------------------------------------------------------------------- |
| `docs`      | Consumer AGENTS.md and workflow docs                   | No (generated at init) | `enable docs --dry-run --json`                                                          |
| `storybook` | Storybook + interaction/axe tests                      | Yes                    | `pnpm --filter @atlas/ui build-storybook && pnpm --filter @atlas/ui test:storybook`     |
| `visual`    | Playwright screenshot baselines (requires `storybook`) | Yes                    | `pnpm --filter @atlas/ui build-storybook && pnpm --filter @atlas/ui test:visual:docker` |
| `perf-ci`   | Lighthouse + bundle GitHub workflows                   | Yes                    | `pnpm perf:lhci` and `pnpm --filter @atlas/web perf:analyze`                            |
| `security`  | `pnpm audit` script + workflow                         | No                     | `pnpm security:check`                                                                   |
| `updates`   | Dependabot                                             | No                     | inspect `.github/dependabot.yml`                                                        |
| `coverage`  | Critical-subsystem coverage floors                     | No                     | `pnpm test:risk-coverage`                                                               |
| `hooks`     | Husky + lint-staged                                    | No                     | exercise the hook in a Git repository                                                   |
| `cursor`    | Cursor rule + skill adapters                           | No                     | `enable cursor --dry-run --json`                                                        |
| `docker`    | Compose scaffold and infra example                     | No                     | `docker compose` locally; image build files already exist from init                     |

`security` fails on high/critical advisories unless a documented exception matches **advisory id,
package name, version, and every finding path**. An exempt finding that is also reachable through a
non-exempt path still fails. Exceptions expire. This is not Gitleaks, SBOM, or governance.

`atlas enable docs` replaces `AGENTS.md` (and related workflow docs) only when the **full file
checksum** matches a known published copy. Phrase matching is not used. Customized docs stay
untouched.

After `storybook`, run `pnpm install` and `pnpm --filter @atlas/ui exec playwright install`. After
`visual`, compare shipped baselines with `pnpm --filter @atlas/ui test:visual:docker` (Playwright
noble image). Do not compare or recapture with host Chromium, and do not use `--update-snapshots` to
silence failures. Recapture only in that image after reviewing every PNG; generated comparison CI
never updates snapshots. Docker enablement expects a committed `pnpm-lock.yaml`
(`--frozen-lockfile`). Lighthouse CI installs Chrome for Testing and sets `CHROME_PATH` before
`pnpm perf:lhci`. Local runs need a Chrome/Chromium binary on `PATH` or `CHROME_PATH`. An optional
`LHCI_GITHUB_APP_TOKEN` can upload GitHub status checks.

Enablement plans every action before writing. `--dry-run` writes nothing. Conflicts skip that
destination and are listed; they do not silently overwrite, and they do not leave undocumented
partial mutations. `package.json` keys are merged only when the key is absent or already identical.
`atlas upgrade` does **not** silently add these capabilities. `visual` requires `storybook` to be
fully installed (`status: installed`), not merely present.

## Existing-consumer adoption

1. Keep using your current CLI for Doctor and for any `atlas upgrade --to <platform-version>`. That
   step does not add Storybook, coverage, or other opt-in files. Do not expect `upgrade --to 1.1.0`
   to install `atlas enable`.
2. Invoke a CLI release that contains `enable` (`pnpm dlx @blitzcraftlabs/atlas@<next-cli-release>`
   until that version is assigned). It may be newer than `platform.baseline.atlasVersion`.
3. `… enable docs --dry-run --json` — replace known unmodified shipped docs only. Review conflicts.
4. Enable each extra capability you want. Run `pnpm install` after Storybook or hooks.
5. Run that capability's `validationCommand`. File presence is not a passing test.
6. Re-run Doctor, lint, typecheck, and tests.

## Maintainer-only

Not offered to generated consumers: npm publication, release rehearsal, BlitzCraft runners,
`pnpm governance:check`, `pnpm docs:check`, `pnpm template:check`, Gitleaks fixtures, and the
`apps/reference` harness. GitHub-native repository settings on `blitzcraftlabs/atlas` (CodeQL
default setup, GitHub Code Quality, secret scanning, Dependabot, branch protection) are also **not**
copied by `atlas init` or `atlas enable`.

See [agents.md](agents.md), [testing.md](testing.md),
[reference-patterns.md](reference-patterns.md), and [upgrades.md](upgrades.md).
